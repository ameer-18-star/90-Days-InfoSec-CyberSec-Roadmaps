90-Day Roadmap For "Information Assurance Analyst" Mastery

An advanced-track plan for practitioners who operate at the intersection of security controls and mission assurance — classifying information systems, executing NIST RMF steps to achieve and maintain Authorization to Operate, assessing STIG compliance, producing security authorization packages that withstand authorizing official scrutiny, and running continuous monitoring programs that keep systems authorized between major assessments.

Phase 1: IA Foundations, System Classification & RMF Execution

Days 1-30: Building the NIST RMF execution capability from system categorization through security control selection and implementation documentation

🎯 Phase 1 Goals

IA Analyst Role Clarity System Categorization (FIPS 199) NIST RMF Step Execution Security Control Selection (SP 800-53) System Security Plan Writing

Week 1: The Information Assurance Analyst Role & IA Ecosystem

  • Study what distinguishes an Information Assurance Analyst from a GRC Analyst (commercial framework compliance), a security engineer (building controls), and a cybersecurity analyst (monitoring threats) — the IA Analyst owns the formal authorization lifecycle of information systems, ensuring they meet defined security requirements before and during operation
  • Learn the IA ecosystem: the relationship between NIST SP 800-37 (RMF), SP 800-53 (security controls), SP 800-53A (assessment procedures), FIPS 199 (categorization), FIPS 200 (minimum security requirements), and how they form a coherent system for managing information system risk
  • Study how the RMF authorization chain works: System Owner, Information System Security Officer (ISSO), Information System Security Manager (ISSM), Authorizing Official (AO), and Security Control Assessor (SCA) — and what the IA Analyst is responsible for supporting at each role level
  • Learn how DoD and federal civilian IA programs differ: DISA STIGs vs. NIST baselines, DoD RMF (governed by DoDI 8510.01) vs. federal civilian RMF, and the role of tools like eMASS and Xacta in tracking authorization packages
  • Study the concept of Authorization to Operate (ATO): what it means, why systems require it, what happens when a system operates without one, and why continuous monitoring is required to maintain it between assessment cycles
  • Review one real public System Security Plan (SSP) structure (from NIST's SP 800-18 template) and annotate every section with what evidence an IA Analyst would need to gather to populate it for a real system
  • Learn how IA Analysts must think simultaneously about two distinct audiences: the technical team implementing controls (who need specific, actionable requirements) and the Authorizing Official (who needs evidence that risks are understood and managed)
  • Document a personal IA Analyst role charter covering the authorization lifecycle stages you intend to own, the frameworks you'll focus on, and your operating principles for producing authorization packages that withstand rigorous assessment

Week 2: System Categorization & Information Type Analysis

  • Study FIPS 199 in depth: how information types are defined, how confidentiality/integrity/availability impact levels are assigned to each information type, and how the system's overall security categorization is derived from the high-water mark across all information types
  • Learn NIST SP 800-60 (Guide for Mapping Types of Information and Information Systems to Security Categories): how to use Volume II's information type tables to assign provisional impact levels and when the IA Analyst must override the provisional with a justified higher or lower assignment
  • Practice categorizing 3 fictional information systems: a healthcare patient records system, a financial transaction processing system, and an internal HR management system — producing a complete FIPS 199 categorization worksheet for each with information type listings and impact level justifications
  • Study what triggers a recategorization: new information types being processed, changes in the sensitivity of existing information, changes in the system boundary, or a significant change that affects the system's threat profile
  • Learn how system boundary definition affects categorization: what is inside the system boundary (and therefore subject to RMF), what is inherited from a common control provider, and how inheritance changes what the IA Analyst must document
  • Practice defining the system boundary for a fictional cloud-hosted application including inherited controls from the cloud provider's FedRAMP authorization and identifying which controls remain the system owner's responsibility
  • Study how the security categorization drives every subsequent RMF step: it determines the baseline control set, the assessment rigor, and the risk posture the AO must accept or reject
  • Document a complete system categorization methodology covering FIPS 199 worksheets, SP 800-60 information type mapping, boundary definition, and inheritance identification for a fictional enterprise system

Task heading at the end of week: System Categorization Package

Produce complete FIPS 199 categorization worksheets for 3 fictional systems using SP 800-60 information type mapping, define system boundaries and inherited controls for a cloud-hosted system, and document a reusable categorization methodology with recategorization triggers.

Week 3: Security Control Selection & Tailoring

  • Study NIST SP 800-53 Rev 5 in depth: its control family structure, the distinction between base controls and control enhancements, and how the control catalog is organized around protection requirements rather than threat types
  • Learn how to select a security control baseline for a given system categorization: LOW, MODERATE, or HIGH baseline from NIST SP 800-53B, and how organization-defined parameters (ODPs) within controls must be filled in with specific values rather than left as placeholders
  • Practice selecting the MODERATE baseline for a fictional financial system and tailoring it: scoping (removing controls that don't apply due to the system's operational environment), compensating (adding alternative controls where baseline controls are infeasible), and supplementing (adding controls above the baseline for specific high-risk areas)
  • Study how to assign controls to implementation layers: system-specific controls (implemented by the system owner), hybrid controls (partially system-specific, partially inherited), and common controls (fully inherited from an enterprise common control provider)
  • Learn how to document common control inheritance in an SSP: identifying the common control provider, referencing their authorization package, and documenting exactly which controls and enhancements are being inherited
  • Practice documenting the control allocation for a fictional system using a three-column spreadsheet: control, implementation type (system/hybrid/inherited), and responsible party for each control in the MODERATE baseline
  • Study how tailoring decisions must be justified in the SSP and reviewed by the AO: removing a control is not a technical decision but a risk acceptance decision that requires explicit AO agreement
  • Document a complete security control selection and tailoring package for a fictional MODERATE-categorization system including ODP values, tailoring justifications, and control allocation spreadsheet
NIST SP 800-53 Rev 5 MODERATE Baseline ODP Population Control Tailoring

Task heading at the end of week: Security Control Selection Package

Select and tailor the MODERATE baseline for a fictional financial system with justified scoping decisions and populated ODPs, produce a three-column control allocation spreadsheet distinguishing system-specific, hybrid, and inherited controls, and document tailoring justifications for every removed control.

Week 4: System Security Plan Writing & Documentation Standards

  • Study what makes an SSP acceptable to an Authorizing Official: every control implementation description must be specific enough for an assessor to verify — "we use firewalls" fails, "boundary protection is implemented via a Palo Alto PA-5250 configured with the following rule set, reviewed quarterly, managed by [team]" passes
  • Learn the SSP's required sections (per NIST SP 800-18): system description, system categorization, authorization boundary diagram, network architecture diagram, data flow diagram, control implementation descriptions, and responsible parties for each control
  • Practice writing control implementation descriptions for 10 controls from the MODERATE baseline — writing each description at a level of specificity that an independent assessor could use to develop test procedures without additional clarification
  • Study how to write a system description that gives the AO a clear understanding of the system's mission, its data flows, its interconnections, and its technical architecture — in language that is accurate enough for technical reviewers and clear enough for the AO who may not be deeply technical
  • Learn how to produce the SSP's required diagrams: authorization boundary diagram showing what is inside and outside the ATO boundary, network diagram showing system components and network segments, and data flow diagram showing how information moves through the system and where it is protected
  • Practice producing authorization boundary, network, and data flow diagrams for a fictional 3-tier web application hosted in AWS, including inherited FedRAMP controls from the cloud provider
  • Study how to manage SSP version control and update cadence: when a significant change triggers a full SSP revision vs. an interim change record, and how to track the SSP through its review and approval cycle
  • Document a complete SSP template ready for real use, with guidance notes on each section explaining what information is required and what level of specificity is acceptable to an AO
SSP Writing (SP 800-18) Control Implementation Descriptions Authorization Boundary Diagrams Data Flow Diagrams

Task heading at the end of week: System Security Plan & Authorization Package Diagrams

Write 10 control implementation descriptions at AO-acceptable specificity for the MODERATE baseline, produce authorization boundary, network, and data flow diagrams for a fictional AWS-hosted system, and complete a full SSP template with populated system description and guidance notes on every section.

Phase 2: Security Assessment, STIG Compliance & ATO Package Completion

Days 31-60: Running security control assessments, managing STIG-based compliance, and producing the complete ATO package that an Authorizing Official can act on

🎯 Phase 2 Goals

Security Control Assessment STIG & SRG Compliance SAR & POAM Writing Risk Determination ATO Package Assembly

Week 5: Security Control Assessment Using SP 800-53A

  • Study NIST SP 800-53A Rev 5 in depth: how assessment objectives are structured (the "determine" statements for each control), the three assessment methods (examine, interview, test), and how to select appropriate assessment procedures for each control based on the system's impact level
  • Learn how to develop a Security Assessment Plan (SAP): scoping the assessment, defining the assessment methods for each control, specifying the assessment objects (documents to examine, personnel to interview, systems to test), and setting the testing schedule
  • Practice writing a Security Assessment Plan for a fictional system's MODERATE baseline, selecting appropriate assessment methods for 10 controls and documenting the specific assessment objects for each
  • Study how to conduct an assessment interview: the questions to ask system administrators, developers, and security personnel for each control family — what "examine" means when reviewing configuration documentation, and what "test" means when running a scan or trying a specific action
  • Learn how to document assessment findings: the distinction between a "Satisfied" finding (control is implemented as described and is effective), "Other Than Satisfied" finding (control is not implemented, is partially implemented, or is implemented incorrectly), and "Not Applicable" (control does not apply to this system)
  • Practice documenting assessment findings for 5 controls against a fictional system, writing each finding with enough specificity that a remediation engineer can identify exactly what needs to be fixed and an AO can understand the residual risk if it is not fixed
  • Study how assessors distinguish between a control that is technically implemented but documented incorrectly (implementation issue only) and a control that is genuinely not functioning as intended (both an implementation and a risk issue)
  • Document a complete assessment methodology covering SAP development, assessment method selection, finding documentation standards, and the distinction between documentation and implementation deficiencies
NIST SP 800-53A SAP Development Examine / Interview / Test Finding Documentation

Task heading at the end of week: Security Assessment Plan & Finding Documentation

Write a Security Assessment Plan for a fictional MODERATE system selecting assessment methods for 10 controls, then document assessment findings for 5 controls with Satisfied/OTS determination and specific remediation guidance for each OTS finding.

Week 6: STIG & SRG Compliance Assessment

  • Study how DISA STIGs (Security Technical Implementation Guides) and SRGs (Security Requirements Guides) work: STIGs are technology-specific implementation guidance, SRGs are technology-category requirements, and both map to NIST SP 800-53 controls — understanding the mapping allows IA Analysts to use STIG findings as evidence for RMF control assessments
  • Learn how to read a STIG: the STIG Viewer interface, the finding severity categories (CAT I/II/III mapping to High/Medium/Low), the check content (how to assess whether the finding applies), and the fix text (how to remediate)
  • Practice using DISA STIG Viewer (or OpenSCAP) to assess a fictional Windows Server system against the Windows Server 2022 STIG, documenting Open, Not a Finding, Not Applicable, and Not Reviewed findings for at least 20 STIG checks
  • Study how to write a STIG finding explanation that justifies a "Not Applicable" determination: the rationale must be specific and defensible — "this STIG check does not apply because this server does not host a web server" is acceptable; "N/A" alone is not
  • Learn how to map STIG findings to POA&M entries: every Open finding becomes a POA&M entry unless the risk is formally accepted, and every Open CAT I finding requires immediate escalation and documented AO awareness
  • Practice mapping 5 fictional STIG Open findings to POA&M format: finding description, risk level, planned remediation action, scheduled completion date, and responsible party for each
  • Study how automated SCAP (Security Content Automation Protocol) scans generate STIG assessment results and how IA Analysts validate automated scan results against manual verification for ambiguous findings
  • Document a complete STIG assessment methodology covering STIG Viewer use, finding categorization and justification standards, SCAP automation integration, and STIG-to-POA&M mapping procedures
DISA STIG Viewer CAT I / II / III Findings OpenSCAP / SCAP STIG-to-POA&M Mapping

Task heading at the end of week: STIG Assessment & POA&M Mapping

Assess a fictional system against a DISA STIG for at least 20 checks with Satisfied/OTS/N/A/NR determination and written N/A justifications, then map 5 Open findings to POA&M format with remediation plans and scheduled completion dates.

Week 7: SAR Writing, POA&M Management & Risk Determination

  • Study how to write a Security Assessment Report (SAR) that serves the AO's decision-making need: the SAR must present assessment findings clearly, assess the risk each finding poses to the system's mission, and give the AO a clear overall risk determination — not just a list of findings
  • Learn how to determine residual risk from assessment findings: considering the threat source, vulnerability severity, likelihood of exploitation, and impact to CIA — and how to express the combined risk in terms the AO can act on (Acceptable, Acceptable with Conditions, or Unacceptable)
  • Practice writing a Security Assessment Report for a fictional system with 12 assessment findings: summarizing findings by severity and control family, writing the risk determination narrative for the 3 highest-risk findings, and producing an overall risk posture statement
  • Study Plan of Action and Milestones (POA&M) management: what a well-managed POA&M looks like vs. one that is used to bury unresolved risks — milestone dates that are missed repeatedly, findings with no assigned owner, and risks that have been "in remediation" for years all indicate a poorly managed POA&M
  • Learn how to write POA&M entries that are actionable: the weakness description must be specific enough for the remediation engineer to know exactly what to fix, the planned remediation must be a specific technical action (not "implement security controls"), and the scheduled completion date must be realistic
  • Practice writing 5 POA&M entries for a fictional set of assessment findings, each with a specific weakness description, risk rating, planned action, milestone dates, and responsible party
  • Study how to manage inherited control deficiencies: when a common control provider's assessment reveals a deficiency in an inherited control, how the system ISSO documents the impact on their system's risk posture and whether a local compensating control is required
  • Document a complete SAR and POA&M management guide covering finding-to-risk translation, SAR narrative structure, risk determination language, and POA&M entry quality standards
SAR Writing POA&M Management Risk Determination Narrative Residual Risk Assessment

Task heading at the end of week: Security Assessment Report & POA&M Package

Week 8: ATO Package Assembly & Authorization Decision Support

  • Study what a complete ATO package contains: the SSP, SAP, SAR, POA&M, privacy impact assessment (if applicable), contingency plan, incident response plan, and the authorization decision memorandum — and how the IA Analyst assembles and manages this package through the authorization process
  • Learn how to write an Executive Summary for the ATO package that gives the AO exactly what they need to make an authorization decision: the system description, the security categorization, the assessment scope, the key risks, and the recommended authorization decision with rationale — in under 3 pages
  • Practice writing an Authorization Decision Executive Summary for a fictional system with 3 High findings, 8 Medium findings, and a clear recommended path: authorize with conditions (the 3 High findings must be remediated within 90 days)
  • Study how to navigate the Authorization Decision: what "Authorize to Operate," "Authorize to Operate with Conditions," "Deny Authorization to Operate," and "Interim Authorization to Operate" mean — and how each affects the system's operation and the IA Analyst's subsequent responsibilities
  • Learn how to manage the authorization decision timeline: the statutory requirements for ATO duration (3 years maximum under FISMA for federal systems), what triggers a re-authorization before the expiration date, and how to track expiration and initiate re-authorization proactively
  • Practice writing a Significant Change Request for a fictional system adding a new cloud storage integration to an authorized system — documenting the change, its impact on the system categorization and control set, and whether it requires a full re-authorization or a change-level assessment
  • Study how eMASS or equivalent authorization tracking tools are used to manage the authorization package, track POA&M milestones, and generate required FISMA reporting
  • Document a complete ATO package assembly guide covering package component checklist, executive summary writing, authorization decision types, expiration tracking, and significant change management

Task heading at the end of week: Complete ATO Package & Executive Summary

Phase 3: Continuous Monitoring, Supply Chain Risk & Career Readiness

Days 61-90: Running ongoing authorization maintenance, managing supply chain risk, and the certification/interview push

🎯 Phase 3 Goals

Continuous Monitoring Program ConMon Reporting Supply Chain Risk Management (SCRM) Privacy Impact Assessment Interview Readiness

Week 9: Continuous Monitoring Program Design & Execution

  • Study how continuous monitoring (ConMon) is the mechanism that allows a system to maintain its ATO between formal assessment cycles: automated scanning, ongoing assessment of a subset of controls, incident tracking, change management, and periodic reporting to the AO provide ongoing assurance that the risk posture hasn't materially changed
  • Learn how to design a Continuous Monitoring Strategy (per NIST SP 800-137) covering: what will be monitored (control subset selection, automated metrics), how it will be monitored (scanning frequency, manual review cadence), how monitoring results will be reported to the AO, and what findings trigger an out-of-cycle assessment or ATO suspension
  • Practice designing a ConMon strategy for a fictional MODERATE-categorization system: selecting a quarterly manual control review subset, specifying weekly vulnerability scan frequency, defining the security metric dashboard content, and establishing the thresholds that trigger escalation to the AO
  • Study how to produce a ConMon status report: summarizing the current state of the POA&M (milestones met, milestones missed, new findings added), the results of automated scanning, any significant changes processed, and the overall AO attestation that the system's risk posture remains acceptable
  • Learn how to manage findings discovered during ConMon: new findings added to the POA&M, the process for determining whether a new finding changes the system's overall risk posture materially, and when a new finding requires immediate AO notification rather than routine POA&M tracking
  • Practice writing a quarterly ConMon status report for a fictional system: POA&M status summary, scan results summary, 2 new findings discovered and added to the POA&M, and AO attestation narrative
  • Study how to manage ATO expiration proactively: the timeline for initiating re-authorization (12 months before expiration for complex systems), what triggers an interim authorization, and how to manage a system operating on an expired ATO
  • Document a complete continuous monitoring program design covering strategy development, control subset selection, reporting cadence, escalation thresholds, and re-authorization timeline management
NIST SP 800-137 ConMon Strategy Quarterly Status Reports ATO Expiration Management

Week 10: Supply Chain Risk Management & Privacy Impact Assessment

  • Study how SCRM (Supply Chain Risk Management) has become a first-class IA concern: NIST SP 800-161 and the SR control family in SP 800-53 Rev 5 require IA Analysts to assess and document risks from hardware, software, and service providers — not just the system itself
  • Learn how to conduct a supply chain risk assessment for a fictional system: identifying critical components and their suppliers, assessing the risk associated with each supplier (country of origin, financial stability, security practices, incident history), and documenting mitigations for high-risk supply chain relationships
  • Practice producing a supply chain risk assessment for a fictional network appliance whose firmware is developed by a foreign subsidiary: documenting the risk, the applicable SR controls, and compensating measures (firmware integrity verification, network traffic monitoring, contractual security requirements)
  • Study how to conduct a Privacy Impact Assessment (PIA): identifying personally identifiable information (PII) the system collects, processes, or stores, assessing the privacy risks, and documenting the privacy controls that mitigate each risk per NIST SP 800-122 and OMB Circular A-130
  • Learn how the Privacy Act of 1974 and the E-Government Act of 2002 create specific documentation requirements (System of Records Notice for Privacy Act systems) that the IA Analyst must address in the authorization package
  • Practice writing a Privacy Impact Assessment for a fictional HR management system that processes employee PII: identifying PII types, assessing the risks of unauthorized disclosure, and documenting the privacy controls and oversight mechanisms
  • Study how SCRM and privacy requirements interact with FedRAMP: what the cloud provider's FedRAMP authorization covers regarding supply chain and privacy, and what remains the customer agency's responsibility to document
  • Document a complete supply chain risk management guide and a PIA template covering IA-relevant requirements from SP 800-161, SP 800-122, and OMB A-130

Week 11: FedRAMP, Cloud Authorization & IA Program Metrics

  • Learn how to write a FISMA annual report contribution: the metrics and status information the IA program must contribute to the agency's annual FISMA report to OMB and Congress

Project Ideas

Practice projects organized by difficulty to keep building after Day 90

Basic

  • Complete a FIPS 199 categorization for one fictional 2-tier system
  • Select the LOW baseline for a fictional system and identify the applicable controls
  • Write 3 control implementation descriptions at AO-acceptable specificity
  • Assess 10 STIG checks against a fictional system with Sat/OTS/N/A/NR determinations
  • Write 2 POA&M entries with specific weakness descriptions and planned actions
  • Draw an authorization boundary diagram for a simple fictional system
  • Write a brief risk determination narrative for one HIGH-severity finding
  • Identify the inherited controls from a FedRAMP MODERATE IaaS authorization for a fictional system
  • Write a basic ConMon status report for a 3-finding fictional system
  • Identify 3 PII types in a fictional system and the applicable privacy controls

Intermediate

  • Complete a full FIPS 199 categorization package using SP 800-60 for a MODERATE system
  • Select and tailor the MODERATE baseline with justified scoping decisions and populated ODPs
  • Write a full SSP with all required sections and authorization boundary, network, and data flow diagrams
  • Develop a Security Assessment Plan for 10 controls with assessment method selection
  • Conduct a 20-check STIG assessment with written N/A justifications for each N/A finding
  • Write a Security Assessment Report for a 10-finding assessment with risk determination
  • Write 5 POA&M entries at AO-acceptable quality with milestone dates and responsible parties
  • Design a continuous monitoring strategy for a MODERATE system
  • Write a Privacy Impact Assessment for a system processing PII
  • Write a significant change request for a new integration to an authorized system

Advanced

  • Build a complete ATO package for one fictional system: all components coherently referencing the same system
  • Produce a FedRAMP leverage authorization package including customer responsibility implementation summary
  • Conduct a 30+ check STIG assessment and map all Open findings to a complete POA&M
  • Write a complete SAR with overall risk determination and recommended authorization decision for a 12-finding assessment
  • Design a ConMon program for a 5-system portfolio with portfolio-level dashboard and FISMA reporting contribution
  • Produce a supply chain risk assessment for a system with a high-risk foreign component
  • Write an IA program metrics dashboard and FISMA annual report contribution for a fictional agency
  • Write an Authorization Decision Executive Summary for an AO with 3 High findings and recommended ATO with conditions
  • Develop a complete system re-authorization package for a fictional system approaching ATO expiration
  • Mentor a junior security practitioner through their first control assessment and SSP contribution

Expert

  • Build a complete end-to-end RMF authorization package for a fictional complex multi-tier system
  • Design and document an IA program for a fictional federal agency with 20-system portfolio
  • Publish original guidance on a specific RMF challenge (FedRAMP inheritance, SCRM implementation, or ConMon automation)
  • Contribute to a public RMF or FedRAMP community forum as a subject matter expert
  • Design a complete IA analyst apprenticeship curriculum for practitioners new to the federal/DoD environment
  • Build an automated ConMon evidence collection and reporting pipeline for a fictional system portfolio
  • Develop a complete IA program maturity model for organizational self-assessment
  • Mentor multiple practitioners through their first ATO packages
  • Design a supply chain risk program spanning a fictional agency's entire system portfolio
  • Present an IA program status and risk posture to a real or simulated AO-level audience

What Next

Where to take your IA Analyst career after Day 90

1. Specialize or Broaden

  • Decide: move toward ISSO / ISSM ownership, specialize as a security control assessor (3PAO/SCA), pursue FedRAMP consulting, or broaden toward IA program management
  • Consider the ISSO track if you want to own the full authorization lifecycle for a specific system portfolio
  • Consider the SCA / 3PAO assessor track if assessment and findings documentation energized you most
  • Consider FedRAMP consulting if you want maximum exposure to diverse cloud authorization packages and client environments
  • Pursue CAP (now CGRC) as your next certification — it is the most directly recognized credential for this role
  • Pursue CISSP once you have the experience requirement — it significantly expands your access to senior IA and program leadership roles
  • Join ISACA and ISC2 local chapters for professional development and networking
  • Set a 6-12 month direction-setting goal
  • Identify one area of RMF or FedRAMP where your knowledge still has gaps and plan to close it
  • Consider which agency or contractor environment gives you the most complex authorization challenges for fastest skill development

2. Apply & Network

  • Apply to Information Assurance Analyst / ISSO / RMF Analyst / Cybersecurity Compliance Analyst roles weekly
  • Tailor your resume per job description, emphasizing specific RMF steps executed and authorization packages supported
  • Attend ISACA local chapter meetings and federal security community events
  • Reach out to ISSOs, ISSMs, and IA program managers on LinkedIn for informational conversations
  • Keep your portfolio updated with new authorization artifacts and assessment work
  • Practice behavioral mock interviews monthly using STAR format for your SSP writing, risk determination, and AO escalation stories
  • Ask for referrals once you have built real community connections
  • Track applications and follow up professionally
  • Target federal agencies and DoD contractors with large system portfolios — the volume of authorization work accelerates your skill development fastest
  • Set a weekly application/networking quota and stick to it

3. Keep Building

  • Stay current with NIST SP 800-53 updates, FedRAMP changes, and DISA STIG version releases
  • Re-read one NIST SP 800-series publication per month and annotate it with practical application notes
  • Write a monthly post about an RMF decision, a categorization challenge, or a STIG assessment finding
  • Build a second, more advanced authorization package artifact every 90 days
  • Track new regulatory requirements (OMB memoranda, CISA directives) and their impact on RMF documentation
  • Mentor junior practitioners through their first system categorization or SSP section
  • Read one governance or compliance management book per quarter for broader IA program context
  • Attend at least one federal cybersecurity conference or ISACA webinar per quarter
  • Reassess your roadmap every quarter and adjust goals
  • Seek opportunities to review a peer's SSP or SAR and provide detailed feedback

4. Give Back

  • Turn your 90-day notes into content for Virtual Mentors SOIT
  • Create a "how RMF actually works in practice" series for practitioners new to the federal/DoD environment
  • Answer RMF and IA questions in community forums, LinkedIn groups, and Discords regularly
  • Open-source one of your templates (categorization worksheet, SSP template, ConMon strategy) for others to use
  • Host a free workshop on writing control implementation descriptions that satisfy an AO
  • Write a "lessons learned" retrospective on your 90 days publicly
  • Pair up with another aspiring IA Analyst for authorization package peer review accountability
  • Contribute feedback to a NIST public comment period on an SP 800-series publication update
  • Review and give feedback on a peer's risk determination narrative or POA&M entry
  • Pay it forward — share this exact roadmap with someone starting out

✅ Developed a Security Assessment Plan, conducted a 20+ check STIG assessment, and written a SAR with risk determination | ✅ Built a complete ATO package with authorization executive summary and POA&M | ✅ Designed a continuous monitoring strategy and written a quarterly ConMon status report


Technologies Covered: NIST SP 800-37/53/53A/60/137/161/18, FIPS 199/200, DISA STIG Viewer, OpenSCAP/SCAP, eMASS/Xacta, FedRAMP templates, Visio/draw.io (authorization diagrams), Nessus/Tenable (STIG scanning), POA&M tracking tools, CAP/CGRC certification framework.


Remember: The IA Analyst's job is not to produce documentation for its own sake — it is to give the Authorizing Official a clear, honest picture of what risks exist in a system so that risk acceptance is an informed decision rather than a hope. Every categorization you complete, every control you document, every finding you assess, and every POA&M entry you write exists to answer one question: "does the person accepting the risk of operating this system understand what they are accepting?" Write with that reader in mind, always — and the authorization package will be worth the effort it takes to produce.
