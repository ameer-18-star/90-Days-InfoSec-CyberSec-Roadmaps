90-Day Roadmap For "Cloud Security Engineer" Mastery

An advanced-track plan for practitioners ready to move beyond monitoring dashboards and into building the cloud security controls themselves — engineering guardrail policies, implementing workload identity, authoring detection pipelines, and writing the automation that keeps cloud environments continuously compliant without human-in-the-loop remediation for every finding.

Phase 1: Cloud Security Engineering Foundations & IAM Hardening

Days 1-30: Building the infrastructure-engineering mindset and owning cloud identity as the foundational security control layer

🎯 Phase 1 Goals

Cloud Security Engineering Mindset IAM Hardening SCPs & Permission Boundaries Workload Identity Federation Secrets Management

Week 1: The Cloud Security Engineer Role & Engineering Mindset

  • Study what distinguishes a cloud security engineer from a cloud security analyst (triage and monitoring), a DevSecOps engineer (pipeline gates and IaC scanning), and a cloud architect (landing zone design) — the engineer builds and operates the controls the analyst monitors and the architect designed
  • Learn how cloud security engineering shifts from reactive (alert → investigate → remediate manually) to preventive (policy → guardrail → automated enforcement) — treating every recurring remediation as a future automation target
  • Study how cloud security engineers work across the shared responsibility boundary: what the provider controls, what the customer must engineer, and where the gaps live that require custom automation
  • Learn how infrastructure-as-code (IaC) is the cloud security engineer's native medium — every control, every policy, every guardrail is code that lives in version control, gets peer-reviewed, and deploys through a pipeline
  • Study how to audit an existing cloud environment for security control gaps: what's missing, what's misconfigured, and what's present but not enforced
  • Practice running a Prowler or ScoutSuite scan against a lab AWS or Azure environment and categorizing findings by control gap type
  • Learn how cloud security engineers document their work: runbooks, ADRs, and control implementation docs that let the next engineer understand what was built and why
  • Document a personal cloud security engineering charter: your target cloud platform(s), control ownership scope, and IaC-first operating principles
Engineering vs. Monitoring Mindset Shared Responsibility IaC-First Operations Prowler / ScoutSuite

Task heading at the end of week: Cloud Security Control Gap Audit

Run a security posture scan against a lab cloud environment, categorize every finding by control gap type, and document a personal IaC-first engineering charter covering platform scope and operating principles.

Week 2: Cloud IAM Hardening — SCPs, Permission Boundaries & Least Privilege

  • Study how AWS Service Control Policies (SCPs) and Azure Policy / GCP Organization Policies work as preventive guardrails — they deny actions before they happen rather than alerting after the fact
  • Learn how to write SCPs that enforce least privilege at the organization level: denying dangerous actions across every account simultaneously — disabling CloudTrail, leaving S3 buckets public, attaching admin policies
  • Practice writing and testing 5 SCPs in a lab: disable root user API access, restrict to approved regions, deny public S3 ACLs, require MFA for sensitive actions, and restrict IAM policy creation to approved patterns
  • Study how AWS IAM Permission Boundaries work as a second guardrail layer: delegating IAM management to teams while ensuring they cannot create permissions that exceed their own boundary
  • Learn how to audit existing IAM roles and policies for privilege escalation paths using automated tools and manual review techniques
  • Practice using IAM Access Analyzer, Cloudsplaining, or CloudMapper to identify over-permissioned roles and privilege escalation paths in a lab environment
  • Study how to implement IAM least privilege at scale across hundreds of roles without creating operational friction that causes teams to work around controls
  • Document a complete SCP library and IAM hardening runbook covering the 10 highest-impact preventive guardrails for an AWS multi-account environment
AWS SCPs Azure Policy Permission Boundaries IAM Access Analyzer

Task heading at the end of week: SCP Library & IAM Hardening Runbook

Write and test 5 SCPs in a lab environment, use IAM Access Analyzer to identify privilege escalation paths, and document a 10-SCP library with deployment and testing instructions for a multi-account environment.

Week 3: Workload Identity & Secrets Management Engineering

  • Study why workload identity is the highest-impact IAM engineering problem in modern cloud: long-lived static credentials are the dominant cloud breach vector and entirely avoidable with proper workload identity design
  • Learn how AWS IAM Roles for Service Accounts (IRSA), Azure Workload Identity Federation, and GCP Workload Identity work — how short-lived tokens replace long-lived keys using cryptographic trust between the cloud provider and the workload's identity
  • Practice implementing IRSA for a Kubernetes workload in a lab: creating the OIDC provider, annotating the service account, and scoping the IAM role to least privilege
  • Study how to implement cross-account role assumption patterns securely: trust policy scoping, external ID conditions, and session policy restrictions
  • Learn how to engineer a secrets management architecture using AWS Secrets Manager, Azure Key Vault, or HashiCorp Vault — rotation automation, access auditing, and application integration patterns
  • Practice building a Secrets Manager rotation Lambda for a database credential, testing the rotation end-to-end in a lab environment
  • Study how to detect and remediate existing long-lived credentials: credential age reporting, automated notification, and forced rotation workflows
  • Document a complete workload identity implementation guide and a secrets management engineering runbook covering rotation, auditing, and application integration patterns
IRSA / Workload Identity Federation OIDC Trust Secrets Manager / Key Vault Credential Rotation Automation

Task heading at the end of week: Workload Identity Implementation & Secrets Rotation

Implement IRSA for a Kubernetes workload in a lab, build an automated secrets rotation Lambda for a database credential, and document the full workload identity and secrets management runbook.

Week 4: Cloud Logging Architecture & Centralized Telemetry Engineering

  • Study how cloud security engineers own the logging pipeline — ensuring every relevant event is captured, centralized, integrity-protected, and available to the detection team before an incident, not during
  • Learn how to architect a centralized logging account: CloudTrail org trail, S3 log bucket with Object Lock, and CloudWatch Logs Insights for multi-account visibility
  • Practice building a CloudTrail organization trail in a lab: enabling it across all accounts, shipping to a centralized log account, and configuring Object Lock to prevent tampering
  • Study which specific log sources every cloud security program must capture: CloudTrail management and data events, VPC Flow Logs, DNS query logs, S3 access logs, IAM credential reports, and container runtime logs
  • Learn how to calculate and manage cloud logging costs — ingestion and storage add up quickly and a cloud security engineer must design cost-efficient logging without creating coverage gaps
  • Practice writing an S3 bucket policy and KMS key policy that protect log integrity from modification even by the account's own administrators
  • Study how to validate logging coverage — confirming every account, region, and service that should be logging actually is, and alerting on coverage gaps
  • Document a complete cloud logging architecture guide covering source-to-SIEM pipeline, integrity protection, cost optimization, and coverage validation for a multi-account environment
CloudTrail Org Trail S3 Object Lock VPC Flow Logs Log Integrity Protection

Task heading at the end of week: Centralized Cloud Logging Architecture

Build a CloudTrail organization trail with centralized log account, Object Lock, and KMS protection in a lab, and document a complete logging architecture guide with source coverage checklist and gap-alerting design.

🎯 Milestone 1 Achievement

You can audit a cloud environment for control gaps, engineer preventive IAM guardrails with SCPs and permission boundaries, implement workload identity to eliminate static credential risk, build automated secrets rotation, and architect a centralized multi-account logging pipeline with integrity protection — the foundational engineering toolkit of a Cloud Security Engineer.

Phase 2: Network Security Engineering, Detection Pipelines & Automation

Days 31-60: Engineering cloud network controls, building detection at scale, and writing the automation that closes findings without human-in-the-loop remediation

🎯 Phase 2 Goals

VPC Security Engineering Cloud Network Controls Detection Rule Engineering Automated Remediation Security Automation (Lambda / Functions)

Week 5: Cloud Network Security Engineering

  • Study how cloud network security engineering differs from traditional perimeter networking: security groups and NACLs are software-defined, stateful, and programmable at scale — the engineer who writes the Terraform owns the enforcement
  • Learn how to design and implement a multi-tier VPC: public subnets for load balancers, private subnets for application workloads, isolated subnets for data tiers, with security group rules enforcing tier-to-tier flow controls
  • Practice building a 3-tier VPC with Terraform: Internet Gateway, NAT Gateway, route tables, security group rules with least-privilege egress, and VPC Flow Log enablement
  • Study how to engineer AWS Network Firewall or Azure Firewall for deep-packet inspection and URL-based egress filtering for workloads that require internet access
  • Learn how to implement VPC endpoints (AWS PrivateLink) and Private Endpoints (Azure) to route AWS/Azure API traffic through private network paths, eliminating internet exposure for service API calls
  • Practice implementing VPC endpoints for S3, Secrets Manager, and EC2 APIs in a lab, updating security group rules to allow only endpoint-routed traffic
  • Study how to detect and auto-remediate common network misconfigurations: overly permissive security groups, missing VPC Flow Logs, and unencrypted traffic flows
  • Document a complete cloud network security engineering runbook covering VPC design patterns, security group policy, VPC endpoint implementation, and egress filtering
Terraform VPC Security Groups & NACLs AWS Network Firewall VPC Endpoints / PrivateLink

Task heading at the end of week: Multi-Tier VPC & Network Control Implementation

Build a complete 3-tier VPC in Terraform with security group rules, NAT Gateway, VPC Flow Logs, and VPC endpoints for 3 AWS service APIs, with a full network security engineering runbook.

Week 6: Cloud Detection Engineering — Rules, Queries & Alerting

  • Study how cloud detection engineering differs from on-premises SIEM work: event sources are API calls and resource configuration changes, not network packets, and detection logic must account for normal automation traffic that resembles attacker behavior
  • Learn how to write CloudWatch Metric Filters and Alarms (or Azure Monitor alert rules) for CIS AWS Foundations Benchmark detection requirements: unauthorized API calls, root account usage, MFA disablement, security group changes, and CloudTrail disabling attempts
  • Practice writing and testing 5 CloudWatch detection rules in a lab: root account login, console login without MFA, IAM policy attachment to a user, security group ingress opened to 0.0.0.0/0, and S3 bucket policy modification
  • Study how to write Athena queries (or Azure Log Analytics KQL) against CloudTrail logs for threat hunting: data exfiltration patterns, credential abuse, and lateral movement through role assumption chains
  • Learn how to integrate cloud detection findings into a SIEM or security data lake — EventBridge to SNS to Lambda to SIEM ingestion pipeline architecture
  • Practice writing a KQL or Athena query identifying all cross-account role assumptions in the last 30 days, flagging those from unexpected source accounts
  • Study how to tune detection rules to reduce false positives from legitimate automation without creating evasion opportunities — the core signal-to-noise engineering challenge in cloud detection
  • Document a cloud detection rule library covering CIS Benchmark requirements plus 5 custom higher-fidelity threat rules, each with tuning notes and SIEM integration architecture
CloudWatch Metric Filters Athena / KQL Queries CIS Benchmark Detection EventBridge Pipeline

Task heading at the end of week: Cloud Detection Rule Library

Write and test 5 CloudWatch detection rules in a lab, write 3 Athena or KQL threat hunting queries, and document a detection rule library with tuning notes and SIEM integration pipeline architecture.

Week 7: Security Automation — Lambda Remediators & Event-Driven Enforcement

  • Study how security automation transforms the cloud security program: instead of a human remediating every GuardDuty finding or Security Hub alert, a Lambda function evaluates the finding and takes calibrated action automatically
  • Learn how to design event-driven security automation using EventBridge rules: GuardDuty finding → EventBridge → Lambda → remediation action, with notification and audit logging at each step
  • Practice building a Lambda remediator that responds to a GuardDuty "IAMUser/AnomalousBehavior" finding by disabling the IAM user's access keys and notifying the security team via SNS
  • Study how to design safe automation: the remediation action must be reversible, the automation must log everything it did, and false-positive handling must be built in before production deployment
  • Learn how to use AWS Config Rules and Remediation Actions (or Azure Policy Remediation Tasks) for continuous compliance — automatically remediating non-compliant resources as they appear
  • Practice writing a custom AWS Config rule that detects S3 buckets with public access block disabled and triggers automatic remediation to re-enable it
  • Study how to manage Lambda remediators as production systems: version control, testing, rollback procedures, and monitoring for automation failures
  • Document a complete security automation framework covering event-driven design, safe remediation principles, Config Rule authoring, and Lambda remediator lifecycle management
EventBridge Rules Lambda Remediators AWS Config Rules Safe Automation Design

Task heading at the end of week: Event-Driven Security Automation Pipeline

Build a GuardDuty finding to Lambda remediation pipeline in a lab, write a custom Config Rule with automated remediation for S3 public access, and document a security automation framework with safe-remediation design principles.

Week 8: Data Security Engineering — Encryption, KMS & Data Protection Controls

  • Study how cloud data security engineering goes beyond "encrypt everything": key management strategy, key rotation automation, key policy authoring, and ensuring encryption can't be silently disabled determine the actual protection level
  • Learn how to design a KMS key hierarchy for an enterprise: customer-managed keys (CMKs) per data sensitivity tier, key policies with least privilege, and cross-account key sharing patterns
  • Practice creating CMKs in a lab with restrictive key policies: allowing specific IAM roles to encrypt/decrypt, denying key deletion, and enabling automatic annual rotation
  • Study how to use SCPs to enforce encryption at rest: denying creation of unencrypted EBS volumes, RDS instances, S3 buckets without default encryption, and Kinesis streams
  • Learn how to implement S3 data protection controls: bucket policies enforcing HTTPS-only access, SSE-KMS default encryption, Object Lock for immutability, and Macie for sensitive data discovery
  • Practice writing an S3 bucket module in Terraform that enforces all data protection controls by default, requiring explicit opt-out rather than opt-in
  • Study how to implement data perimeter controls using resource policies and VPC endpoint policies to prevent data exfiltration to unauthorized destinations
  • Document a complete cloud data security engineering runbook covering KMS key design, encryption enforcement SCPs, S3 hardening module, and data perimeter implementation
KMS Key Hierarchy CMK Key Policies S3 Data Protection Data Perimeter Controls

Task heading at the end of week: KMS Design & S3 Data Protection Module

Design and deploy a KMS key hierarchy with restrictive key policies in a lab, write a Terraform S3 hardening module enforcing all data protection controls by default, and document the full data security engineering runbook.

Phase 3: Container Security, Security-as-Code & Career Readiness

Days 61-90: Engineering Kubernetes and container security controls, building security-as-code pipelines, and the certification/interview push

🎯 Phase 3 Goals

Kubernetes Security Engineering Container Security Controls Security-as-Code Pipeline Cloud Security Posture Management Interview Readiness

Week 9: Kubernetes & Container Security Engineering

  • Study how Kubernetes security engineering differs from VM-based cloud security: the attack surface includes the API server, the kubelet, etcd, the container runtime, and every workload's network policy — all requiring distinct controls
  • Learn how to engineer Kubernetes RBAC: defining roles and cluster roles with least-privilege verb/resource combinations, binding them to service accounts, and auditing for over-permissioned bindings
  • Practice writing Kubernetes RBAC manifests for a fictional application team: a developer role, an application service account, and an automated CI/CD deployment service account — each with least-privilege scoped to their namespace
  • Study how to implement Kubernetes Network Policies: default-deny all ingress and egress, then explicitly permit only the traffic each workload legitimately requires
  • Learn how to write and enforce Pod Security Admission (PSA) policies (or OPA/Gatekeeper policies) that prevent privileged containers, host path mounts, and containers running as root
  • Practice writing a Gatekeeper ConstraintTemplate that denies any Pod that does not set a non-root runAsUser and that does not set readOnlyRootFilesystem: true
  • Study how runtime security tools (Falco) detect container security threats at execution time — writing Falco rules for privileged execution, unexpected network connections, and sensitive file reads
  • Document a complete Kubernetes security engineering runbook covering RBAC design, Network Policies, Pod Security Admission, and Falco runtime detection rules
Kubernetes RBAC Network Policies OPA / Gatekeeper Falco Runtime Security

Task heading at the end of week: Kubernetes Security Engineering Runbook

Write least-privilege RBAC manifests for 3 workload types, implement a default-deny Network Policy set for a fictional application, write a Gatekeeper ConstraintTemplate preventing root containers, and author 3 Falco runtime detection rules.

Week 10: Security-as-Code Pipelines & IaC Security Enforcement

  • Study how security-as-code pipelines shift security left: every infrastructure change goes through automated security checks in the CI/CD pipeline before it can reach production, not after a misconfiguration is already live
  • Learn how to implement a multi-layer IaC security scanning pipeline: Checkov and tfsec for static analysis of Terraform, Trivy for container image scanning, and OPA/Conftest for custom policy-as-code enforcement
  • Practice building a GitHub Actions workflow that runs Checkov, Trivy, and a custom OPA policy check on every pull request, blocking merge on any HIGH or CRITICAL finding
  • Study how to write custom Rego policies in OPA that enforce organization-specific security requirements that generic scanners don't cover — such as requiring specific tags, enforcing naming conventions for IAM roles, or requiring encryption with specific KMS key ARNs
  • Learn how to manage the policy-as-code lifecycle: version control, testing, exception handling, and keeping policies current as cloud provider APIs evolve
  • Practice writing 3 custom OPA/Rego policies for organization-specific requirements and testing them against both compliant and non-compliant Terraform configurations
  • Study how to handle the false-positive and exception problem in CI/CD security gates without creating a culture of "just suppress the finding" that defeats the pipeline's purpose
  • Document a complete security-as-code pipeline design covering tool selection, custom policy authoring, exception management, and pipeline failure handling
Checkov / tfsec OPA / Rego / Conftest GitHub Actions Pipeline Custom Policy Authoring

Task heading at the end of week: Security-as-Code CI/CD Pipeline

Build a GitHub Actions pipeline running Checkov, Trivy, and custom OPA policies on every pull request with merge blocking on HIGH/CRITICAL findings, and write 3 custom Rego policies for organization-specific requirements.

Week 11: Cloud Security Posture Management & Continuous Compliance Engineering

  • Study how Cloud Security Posture Management (CSPM) works as a continuous control — not a quarterly audit artifact but a real-time view of every resource's compliance state that feeds directly into automated remediation and risk prioritization
  • Learn how to configure AWS Security Hub or Microsoft Defender for Cloud as a centralized CSPM platform: enabling standards (CIS, AWS Foundational, PCI-DSS), aggregating findings across accounts, and integrating with your EventBridge automation pipeline
  • Practice configuring Security Hub across 3 linked accounts in a lab, enabling CIS AWS Foundations standard, and building a dashboard showing compliance posture by account and control category
  • Study how to engineer a continuous compliance reporting pipeline: Security Hub findings to a metrics database to a dashboard that shows compliance trend over time — not just current state but direction of travel
  • Learn how to prioritize CSPM findings for remediation using risk-based scoring: asset criticality, finding severity, exploitability, and whether automated remediation is already in place
  • Practice writing a Lambda that queries Security Hub findings daily, scores them by risk, and generates a prioritized remediation work queue delivered to the engineering team
  • Compile your 90-day work into a single portfolio-style Cloud Security Engineering master document
  • Document a complete CSPM engineering guide covering platform configuration, cross-account aggregation, continuous compliance reporting, and risk-based finding prioritization
