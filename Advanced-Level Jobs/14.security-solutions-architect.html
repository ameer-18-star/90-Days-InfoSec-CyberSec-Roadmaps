90-Day Roadmap For "Security Solution Architect" Mastery

An advanced-track plan for security practitioners ready to move from implementing controls to designing the systems that contain them — translating business requirements, threat intelligence, and risk appetite into concrete reference architectures, technology stack decisions, and integration blueprints that engineers can actually build.

Phase 1: Architecture Thinking, Design Patterns & Threat Modeling

Days 1-30: Shifting from control-level thinking to system-level design — learning how security architects think before they draw

🎯 Phase 1 Goals

Architecture Thinking Security Design Patterns Threat Modeling Reference Architecture Requirements Translation

Week 1: The Security Solution Architect Role & Architecture Thinking

  • Study what distinguishes a security solution architect from a security engineer, a security consultant, and a CISO: architects design systems that others implement, making decisions that are expensive to reverse and that affect everything downstream
  • Learn the core architecture thinking shift: from "how do I configure this control?" to "how should this system be structured so that security is a property of the design, not an afterthought bolted on afterward?"
  • Study how security architects operate at the intersection of business requirements, threat landscape, technology capability, and operational feasibility — all four simultaneously
  • Learn how architects use established frameworks (SABSA, TOGAF with security layers, NIST SP 800-207 Zero Trust) as structured starting points rather than blank-sheet-every-time design
  • Study how architecture decisions create technical debt: a poorly scoped identity architecture in Year 1 becomes the constraint that limits every subsequent security initiative
  • Review one real public reference architecture (AWS Security Reference Architecture, Microsoft Zero Trust guidance, NIST SP 1800 series) and annotate the design decisions visible in the document
  • Learn how to distinguish a reference architecture (reusable pattern) from a solution design (specific implementation for one environment) — both are in scope for this role
  • Document a personal architecture philosophy statement: your principles for how security should be designed into systems, not retrofitted
SABSA Framework Architecture Thinking Design vs. Implementation Technical Debt

Task heading at the end of week: Architecture Philosophy & Reference Architecture Annotation

Annotate one real public reference architecture documenting every visible design decision and its likely rationale, then write a personal architecture philosophy statement covering your core design principles.

Week 2: Security Design Patterns & Foundational Principles

  • Study the foundational security design patterns every architect must know: defense in depth, least privilege, separation of duties, fail-secure defaults, complete mediation, zero trust network access, and assume-breach design
  • Learn how to apply each pattern specifically — not as a checklist item but as a structural decision that shapes how components relate to each other
  • Practice applying 5 design patterns to one fictional system design, documenting explicitly how each pattern changes the architecture vs. a pattern-free naive design
  • Study how design patterns interact and sometimes conflict — least privilege implemented aggressively can conflict with operational availability if not designed carefully
  • Learn how Zero Trust as an architectural principle (never trust, always verify; assume breach; verify explicitly) translates into specific component and network design choices
  • Practice producing a Zero Trust network segmentation design for a fictional hybrid enterprise environment, making the assume-breach principle explicit in every component placement decision
  • Study how security design patterns apply differently across on-premises, cloud-native, and hybrid architectures
  • Document a security design pattern reference library — your personal catalogue of patterns with application examples across different environment types
Defense in Depth Zero Trust Design Least Privilege Architecture Assume-Breach Principle

Task heading at the end of week: Design Pattern Library & Zero Trust Segmentation Design

Build a personal security design pattern library with application examples, and produce a Zero Trust network segmentation design for a fictional hybrid enterprise making assume-breach explicit in every decision.

Week 3: Threat Modeling as an Architecture Discipline

  • Study how threat modeling at the architecture level differs from penetration testing or vulnerability scanning — it's about identifying design flaws before anything is built, not finding bugs in what already exists
  • Learn the primary threat modeling methodologies (STRIDE, PASTA, LINDDUN, attack trees) and how to choose the right one based on the system being designed and the audience reviewing the output
  • Practice running a complete STRIDE threat model for a fictional multi-tier web application, systematically identifying threats against each component and data flow
  • Study how threat modeling output feeds directly back into architecture decisions — a threat model that doesn't change the design is a documentation exercise, not an architecture discipline
  • Learn how to produce a threat model diagram (data flow diagram + trust boundary annotations) that communicates clearly to both engineers and non-technical stakeholders
  • Practice producing a threat model for a fictional cloud-native microservices architecture, documenting the trust boundaries between services and the threats at each boundary
  • Study how threat modeling integrates into the architecture review process and when in a project's lifecycle it should happen (as early as possible, always before detailed design is locked)
  • Document a threat modeling methodology selection guide and a reusable threat modeling process template for use across future architecture engagements
STRIDE PASTA Data Flow Diagrams Trust Boundary Analysis

Task heading at the end of week: STRIDE Threat Model & Cloud Microservices Threat Model

Produce a complete STRIDE threat model for a fictional multi-tier web app and a trust boundary threat model for a fictional cloud-native microservices architecture, each with design change recommendations.

Week 4: Translating Business Requirements into Architecture Decisions

  • Study how security architects translate business requirements (regulatory obligations, risk appetite statements, operational constraints, budget limits) into specific architectural constraints and non-negotiable design decisions
  • Learn how to run a requirements gathering session with business stakeholders that extracts security-relevant requirements they wouldn't think to articulate themselves
  • Practice writing an architecture requirements specification for a fictional fintech company preparing for PCI-DSS compliance, translating regulatory obligations into architecture constraints
  • Study how to document architecture decisions using Architecture Decision Records (ADRs): the decision, the context, the alternatives considered, and the rationale — creating an auditable record of why the design is what it is
  • Learn how to handle conflicting requirements: when business wants maximum user experience and security requires friction, how the architect produces a design that satisfies both as far as possible and documents the tradeoff where not
  • Practice producing 3 ADRs for a fictional identity architecture project, each covering a genuine architectural decision with alternatives and rationale
  • Study how to communicate architecture constraints to stakeholders who see them as blockers rather than enablers — the language of risk, not the language of technical prohibition
  • Document a requirements-to-architecture translation process including a requirements specification template and an ADR template ready for real use
Requirements Specification Architecture Decision Records Constraint Translation Tradeoff Documentation

Task heading at the end of week: Architecture Requirements Spec & ADRs

Write a full architecture requirements specification for a fictional PCI-DSS fintech environment, and produce 3 Architecture Decision Records for an identity architecture project covering real decisions with alternatives and rationale.

🎯 Milestone 1 Achievement

You can articulate the architecture thinking shift from control-level to system-level, apply security design patterns explicitly to real design problems, produce threat models that change architecture decisions, and translate business requirements into documented architecture constraints and decisions — the foundational toolkit of a Security Solution Architect.

Phase 2: Domain-Specific Architecture Design

Days 31-60: Producing deployable reference architectures across identity, cloud, network, data, and application security domains

🎯 Phase 2 Goals

Identity Architecture Cloud Security Architecture Network Security Design Data Security Architecture Application Security Design

Week 5: Identity & Access Management Architecture

  • Study how identity is the new perimeter: in a Zero Trust model, every access decision is an identity decision, and the quality of the identity architecture determines the quality of every downstream control
  • Learn how to design an enterprise identity architecture covering authentication (MFA, passwordless, FIDO2), authorization (RBAC, ABAC, ReBAC), federation (SAML, OIDC, OAuth 2.0), and privileged access governance
  • Practice producing a complete IAM reference architecture for a fictional hybrid enterprise, covering on-premises AD, cloud identity provider, federated SaaS, and privileged access management components
  • Study how to design identity architecture for non-human identities (service accounts, workload identities, machine credentials) — often the most underdesigned and highest-risk identity category
  • Learn how to design a Privileged Access Workstation (PAW) and just-in-time (JIT) access model for administrative access to critical systems
  • Practice producing an ADR for the choice between a flat RBAC model and an attribute-based access control model for a data-sensitive environment
  • Study how identity architecture decisions (directory structure, group design, delegation model) create constraints that affect every other security domain's architecture
  • Document a complete IAM reference architecture package covering all identity layers with integration points and design rationale
RBAC / ABAC / ReBAC Federation (SAML/OIDC) PAM & JIT Access Non-Human Identity

Task heading at the end of week: Enterprise IAM Reference Architecture

Produce a complete IAM reference architecture for a fictional hybrid enterprise covering authentication, authorization, federation, privileged access, and non-human identity, with full ADR documentation.

Week 6: Cloud Security Architecture

  • Study how cloud security architecture differs from on-premises: shared responsibility redraws the ownership boundary, infrastructure is code, and misconfiguration — not exploitation — is the dominant threat vector
  • Learn how to design a cloud security landing zone architecture (AWS, Azure, or GCP) covering account/subscription structure, network topology, IAM delegation, logging pipeline, and guardrail policy enforcement
  • Practice producing a cloud landing zone reference architecture for a fictional organization migrating 3 workload types (web app, data analytics, developer toolchain) to AWS
  • Study how to design cloud-native security controls: SCPs/Azure Policies for guardrail enforcement, VPC/VNET design for network segmentation, KMS for data protection, and CloudTrail/Defender for detection
  • Learn how to architect a secure multi-cloud environment where identity, network, and data controls span more than one cloud provider without creating inconsistent security posture
  • Practice producing an ADR for VPC/VNET network topology design (hub-and-spoke vs. mesh vs. flat) for a security-sensitive multi-region deployment
  • Study how infrastructure-as-code security fits into cloud architecture: IaC security scanning as a guardrail, not an afterthought, and drift detection as a continuous control
  • Document a complete cloud security architecture package covering landing zone, network topology, IAM delegation, and detection pipeline for one cloud provider
Cloud Landing Zone SCPs / Azure Policy VPC / VNET Design IaC Security

Task heading at the end of week: Cloud Security Landing Zone Architecture

Produce a complete cloud landing zone reference architecture for a fictional multi-workload AWS migration, covering account structure, network topology, IAM delegation, guardrail policies, and detection pipeline.

Week 7: Network Security Architecture & Data Security Design

  • Study how network security architecture has evolved: hard perimeter → DMZ model → software-defined segmentation → Zero Trust network access (ZTNA), and how to design for the current era without ripping out functional legacy infrastructure
  • Learn how to design a micro-segmentation architecture for an enterprise environment, defining the segmentation boundaries, traffic flow rules, and enforcement points
  • Practice producing a network security reference architecture for a fictional healthcare organization covering clinical, administrative, IoT/medical device, and remote access segments
  • Study how to design a data security architecture covering data classification, encryption at rest and in transit, tokenization/masking, DLP placement, and data access governance
  • Learn how to architect a data security program for a multi-cloud environment where sensitive data flows across organizational boundaries (SaaS, partners, cloud providers)
  • Practice producing a data security architecture for a fictional financial services organization, mapping controls to data sensitivity tiers and regulatory requirements simultaneously
  • Study how network and data security architectures must be designed together — a network segment boundary that doesn't align with a data classification boundary creates control gaps
  • Document a combined network and data security architecture package for the fictional healthcare organization, showing how the two domains reinforce each other
Micro-Segmentation ZTNA Design Data Classification Architecture Encryption & DLP Placement

Task heading at the end of week: Network & Data Security Reference Architectures

Produce a network security architecture for a fictional healthcare environment and a data security architecture for a fictional financial services organization, each with domain-appropriate design decisions documented.

Week 8: Application Security Architecture & Detection-by-Design

  • Study how application security architecture shifts the OWASP Top 10 conversation from "find these vulnerabilities" to "design the application so these vulnerabilities structurally cannot exist"
  • Learn how to produce an application security reference architecture covering: secure API gateway design, authentication/authorization flows, secrets management integration, input validation boundaries, and security logging requirements
  • Practice producing an application security architecture for a fictional microservices-based SaaS platform, mapping each architecture component to the OWASP threats it structurally mitigates
  • Study how to design a security logging and detection architecture: what telemetry each system layer must emit, how it flows to the detection platform, and what retention and integrity guarantees are required
  • Learn how "detection by design" works — ensuring that every component in an architecture emits the telemetry needed to detect compromise of that component, designed in, not retrofitted
  • Practice producing a detection architecture for the fictional SaaS platform from earlier this week, mapping each component to its required telemetry and the detection use cases that telemetry enables
  • Study how security architects review code and infrastructure designs — what to look for in a design review vs. what belongs in a code review or penetration test
  • Document a complete application security and detection architecture package ready for use as a reference in future SaaS or microservices design engagements
API Security Design Secrets Management Detection by Design Telemetry Architecture

Task heading at the end of week: Application Security & Detection Architecture

Produce an application security architecture for a fictional microservices SaaS platform mapped to OWASP mitigations, and a detection architecture mapping every component to its required telemetry and detection use cases.

🚀 Milestone 2 Achievement

You can produce deployable reference architectures across all five major security domains — identity, cloud, network, data, and application/detection — with design decisions documented in ADRs and threat models attached to each. You can hold a technical design conversation with specialists in any of these domains without losing the cross-domain integration perspective that is the architect's unique contribution.

Phase 3: Technology Evaluation, Architecture Governance & Career Readiness

Days 61-90: Evaluating and selecting security technology stacks, governing architecture decisions at enterprise scale, and the certification/interview push

🎯 Phase 3 Goals

Technology Stack Evaluation Architecture Governance Architecture Review Boards Roadmap & Migration Design Interview Readiness

Week 9: Security Technology Evaluation & Stack Design

  • Study how security architects evaluate and select technology — not by product feature lists but by fit against architecture requirements, integration complexity, operational burden, and vendor risk
  • Learn how to build a technology evaluation framework that weights architectural fit (does this tool fit the design or require the design to flex around the tool?) as a primary criterion
  • Practice building a technology evaluation scorecard for a fictional SIEM platform selection, weighting integration architecture, telemetry ingestion flexibility, detection customization, and operational scalability
  • Study how to design a security technology reference stack — the set of tools and their integration relationships that form the organization's target security architecture
  • Learn how to manage technology portfolio sprawl: when two tools overlap significantly, how the architect makes the rationalization case and manages the migration
  • Practice producing an ADR for a fictional choice between consolidating onto a platform vendor security stack vs. maintaining a best-of-breed point-solution architecture
  • Study how vendor lock-in risk is an architecture concern — designing integration layers that make tool replacement possible without rebuilding the surrounding architecture
  • Document a complete technology evaluation framework and a fictional target security technology reference stack with integration map
Technology Evaluation Framework Security Reference Stack Platform vs. Best-of-Breed Vendor Lock-In Design

Task heading at the end of week: Technology Evaluation Framework & Reference Stack

Week 10: Security Architecture Roadmaps & Migration Design

  • Study how security architects produce multi-year architecture roadmaps that sequence decisions to manage dependency order — you can't build Zero Trust without identity, and you can't build ZTNA without a usable network foundation
  • Learn how to design a security architecture migration from current state to target state, identifying quick wins, critical dependencies, and irreversible decisions that need the most rigor
  • Practice producing a 3-year security architecture roadmap for a fictional organization transitioning from perimeter-centric to Zero Trust design, with phased milestones and dependency sequencing
  • Study how to design a migration without breaking operational security during the transition — maintaining the old controls while building the new architecture in parallel
  • Learn how to quantify architecture roadmap investment in terms a CISO and CFO can evaluate: what each phase costs, what risk it reduces, and what capability it unlocks for subsequent phases
  • Practice writing an architecture investment summary for each phase of your Zero Trust roadmap, framing each phase's business case independently
  • Study how to adapt an architecture roadmap when business priorities shift mid-journey — how to resequence without losing the dependency logic
  • Document a complete architecture roadmap package including phased migration design, dependency map, and per-phase business cases for the fictional Zero Trust transition

Week 11: Architecture Governance & Architecture Review Boards

  • Study how architecture governance works at enterprise scale: the Security Architecture Review Board (SARB) or equivalent body that reviews and approves architectural decisions before they become irreversible commitments
  • Learn how to design an architecture governance process — what triggers a mandatory architecture review, what the review examines, who has approval authority, and how exceptions are handled
  • Practice writing an architecture governance framework covering mandatory review triggers, review criteria, approval tiers, and exception process for a fictional large enterprise
  • Study how to run an architecture review meeting: presenting a proposed design, facilitating constructive challenge from subject matter experts, and producing a clear decision with documented rationale
  • Practice facilitating a mock architecture review session for a fictional cloud migration proposal, with a peer playing skeptical reviewers raising integration and security concerns
  • Study how to handle an architecture review finding where a proposed design has a significant security gap — communicating the concern clearly without blocking legitimate business progress
  • Compile your 90-day work into a single portfolio-style master security architecture package

What Next

Where to take your security architecture career after Day 90

1. Specialize or Broaden

  • Decide: deepen toward enterprise architecture leadership, specialize in one domain (cloud, identity, OT/ICS), or move toward security architecture practice management
  • Consider an Enterprise Security Architect track if cross-domain integration and roadmapping energized you most
  • Consider a Cloud Security Architecture Specialist track if cloud landing zone and cloud-native design stood out
  • Explore security architecture consulting if you want maximum breadth across client environments and industry verticals
  • Consider OT/ICS security architecture as a high-demand specialization with limited available talent
  • Pursue SABSA SCF as the most credentialed signal of architecture-specific expertise
  • Pursue CCSP or cloud provider security specialty certs if the cloud architecture track is the clear direction
  • Join a specialized community for your chosen direction
  • Set a 6-12 month direction-setting goal
  • Identify your industry vertical of deepest interest and build toward recognized expertise in that sector

2. Apply & Network

  • Apply to Security Solution Architect / Security Architect / Enterprise Security Architect / Cloud Security Architect roles weekly
  • Tailor your resume per job description, emphasizing architecture artifacts produced and design decisions owned
  • Attend SABSA Institute community events and working groups
  • Reach out to working security architects on LinkedIn for informational conversations
  • Ask for referrals once you've built real community connections
  • Keep your portfolio updated with new reference architectures and ADR libraries
  • Practice mock architecture walkthrough interviews monthly — verbal fluency explaining your own designs is a core architect interview skill

Remember: Architecture is the discipline of making decisions that are expensive to reverse carefully, and letting the decisions that are cheap to reverse be made later by the people closest to them. Every reference architecture, ADR, and threat model you produce exists to answer one question: "is security a property of this system's design, or a bolt-on that will erode the moment someone needs to go faster?" Design for the threat, document the decision, validate with a threat model, and always close the loop between the architecture on paper and the system that gets built.
